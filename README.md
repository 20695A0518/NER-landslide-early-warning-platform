# PRAHARI

**P**redictive **R**eal-time **A**lerting for **H**azard **A**ssessment in **R**egional **I**nfrastructure

An AI-assisted landslide early-warning and road-connectivity platform for the eight
states of India's North Eastern Region.

> **This is a working prototype, not an operational warning system.** Rainfall is
> generated by a built-in simulator unless you supply an IMD or OpenWeather key,
> SMS is logged to the console unless you configure a gateway, and the model is
> trained on synthetic data. Every one of those facts is surfaced in the product
> itself — see [Honesty about the data](#honesty-about-the-data). Read
> [Before operational use](#before-operational-use) before showing anyone a number
> from this system as if it were a forecast.

---

## What it does

| Requirement | Where it lives |
| --- | --- |
| Rainfall, soil moisture, satellite, terrain and historical inputs | `backend/app/services/weather.py`, `sensors.py`, `app/data/` |
| AI/ML risk prediction | `backend/app/ml/` — hybrid learned + physical model |
| Real-time alerts to authorities and communities | `backend/app/services/alerts.py`, `notifications.py` |
| GIS visualisation of vulnerable roads, villages, infrastructure | `frontend/src/pages/MapView.jsx` |
| Citizen / field-officer geo-tagged photo reporting | `frontend/src/pages/FieldReport.jsx`, `backend/.../reports.py` |
| Dashboards: severity, road status, weather-linked forecast, response priority | `frontend/src/pages/Dashboard.jsx`, `Roads.jsx` |
| Multilingual notifications | `backend/app/services/i18n.py` — 8 languages |
| Low-network / offline operation | `frontend/src/lib/offline.js`, `backend/.../sync.py` |

**Coverage:** 37 monitored slope units across all 8 NER states and 33 districts,
1.13 million people, and 25 road segments totalling 2,121 km.

## Quick start

Two terminals. Python 3.12+ and Node 20+.

**Backend**

```bash
cd backend && python -m venv .venv && .venv/Scripts/python -m pip install -r requirements.txt
```

Train the model (about 40 seconds), then run the API:

```bash
cd backend && .venv/Scripts/python -m app.ml.train && .venv/Scripts/python -m uvicorn app.main:app --reload
```

On Linux/macOS use `.venv/bin/python` instead of `.venv/Scripts/python`.

The first start creates `prahari.db`, seeds all 37 zones, 25 roads, 55 sensor
stations and 8 demo accounts, and runs an initial risk cycle. It is safe to
re-run. API docs at <http://127.0.0.1:8000/docs>.

**Frontend**

```bash
cd frontend && npm install && npm run dev
```

Open <http://localhost:5173>. Vite proxies `/api` and `/media` to the backend.

### Seeing the alerting work

On a normal simulated day the region is quiet, which is correct and
undemonstrative. Go to **System & model → Exercise / drill mode**, pick
*Extreme event*, and run it. That injects a rainfall scenario, re-scores every
slope and drives the full chain: risk escalation → alert issue → multilingual
SMS render → response-priority queue → road status. **Clear drill data** removes
it again.

Or from the API:

```bash
curl -X POST http://127.0.0.1:8000/api/v1/dashboard/drill -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"intensity":"extreme","duration_hours":48}'
```

## How the prediction works

The risk score is **not** a single model output. Three independent lines of
evidence are fused, because each fails differently.

```
                  ┌─────────────────────────┐
  terrain ───────►│  Learned model          │
  rainfall ──────►│  HistGradientBoosting   │──┐
  sensors  ──────►│  + isotonic calibration │  │
                  └─────────────────────────┘  │   weighted
                                               ├── opinion ──┐
                  ┌─────────────────────────┐  │   pool      │
  slope    ──────►│  Physical model         │  │             │
  regolith ──────►│  infinite-slope FoS +   │──┘             │  noisy-OR
  saturation ────►│  ID rainfall threshold  │                ├─ escalation ──► risk
                  └─────────────────────────┘                │
                                                             │
                  ┌─────────────────────────┐                │
  inclinometers ─►│  Observed evidence      │────────────────┘
  field reports ─►│  (can only raise)       │
                  └─────────────────────────┘
```

**Why the physics is there.** When the learned model goes out of distribution —
a new road cut, rainfall beyond anything in the training set — the factor of
safety still gives a defensible answer, and gives a district engineer a quantity
they can argue with rather than an opaque probability.

**Why observed evidence only ever raises the score.** A cracked road reported by
a circle officer is strong evidence something is moving. The *absence* of a
report is very weak evidence of safety, because most NER slopes have nobody
standing on them. Letting silence lower the score would systematically
under-warn exactly the remote villages this platform exists to protect.

### Three modelling decisions worth knowing about

**1. Rainfall thresholds are normalised to local climatology.** 200 mm in 24 h is
an extreme event at Imphal (1,500 mm/yr) and an unremarkable Tuesday at
Mawsynram (11,900 mm/yr). An un-normalised threshold would put the Khasi
escarpment in permanent alarm and train operators to ignore the system.

**2. Strength parameters are recovered by back-analysis, as matric suction.** A
slope standing at 41° demonstrably has FoS > 1 when drained, so any parameter set
computing FoS < 1 for it is wrong. The missing strength is booked as *suction*
cohesion, which decays as the slope saturates — because the strength holding up
a steep regolith slope in fine weather is exactly what a monsoon destroys.
Booking it as permanent cohesion would produce slopes that are stable when dry
*and* stable when saturated, which is the opposite of the behaviour being
modelled. See `app/ml/physics.py`.

**3. Wetness uses drainable porosity, not total porosity.** Most pore volume is
held against gravity at field capacity and never generates positive pore
pressure. Using total porosity would demand ~600 mm to wet a 2 m column — more
than most triggering storms deliver — and the system would read "low" through
the exact events it exists to catch.

Calibration check (`backend/app/ml/physics.py`):

| Scenario | Wetness | Factor of safety |
| --- | --- | --- |
| 1.5 m sandy loam, dry | 0.02 | 1.24 |
| 1.5 m sandy loam, 150 mm/72 h | 0.50 | 0.93 |
| 1.5 m sandy loam, 300 mm/72 h | 1.00 | 0.71 |
| 2.8 m silty clay, 400 mm/72 h | 1.00 | 0.48 |

## Honesty about the data

The most dangerous failure mode for a system like this is not a wrong number —
it is a wrong number that looks authoritative. So:

- **`/system` page** states, in one screen, whether rainfall is measured or
  simulated, whether SMS was really delivered, and that the model was trained on
  synthetic data.
- **`GET /api/v1/dashboard/model`** returns `is_synthetic` and a `caveat` string.
  `app/ml/train.py` writes them; do not remove them.
- **`GET /api/v1/alerts/languages`** reports which translations have been
  reviewed by a native speaker. Currently: none.
- **Drill data** is written with `source="drill"`, never `"imd"`, and raises a
  banner across the platform while present.
- **The seeded landslide inventory is synthetic**, stamped
  `source="synthetic seed"`, and is generated from zone susceptibility so the map
  is coherent. It is not a record of real events and must not be cited as one.

Model metrics from the current synthetic training run — these measure recovery of
the simulator's generating process, **not** real-world skill:

```
ROC-AUC 0.81   PR-AUC 0.50   Brier 0.084   base rate 12.6%
operating threshold 0.10 → recall 0.75
```

Brier score matters more than accuracy here: the evacuation thresholds are set on
the probability, so a stated 70% has to mean roughly seven times in ten.

## Offline behaviour

Built for valleys that lose signal for hours.

- **Installable PWA.** Service worker precaches the shell; map tiles are
  cache-first with a 60-day TTL; API reads are network-first with a 5-second
  timeout falling back to the last good response.
- **IndexedDB outbound queue.** Reports (with photos, downscaled to ~200 KB
  before queueing) are stored locally and survive app closure. A report is only
  removed from the queue after the server acknowledges it.
- **Idempotent replay.** Every report carries a client-generated UUID. A retry
  after an ambiguous failure — request sent, response lost — is deduplicated
  server-side rather than creating a second row.
- **Partial-success sync.** `POST /sync/push` validates each queued report
  individually. One bad GPS fix does not reject the batch, and the offending
  rows are named so the client can drop just those. (This is enforced by a
  regression test; the obvious `list[FieldReportIn]` typing silently breaks it.)
- **One-shot bundle.** `GET /sync/bundle` returns zones, roads, alerts and
  languages in a single request — about 5 KB for one state — because every extra
  round trip on 2G is another chance to fail halfway. `?since=` gives a delta.
- **Code-split frontend.** The two screens a field officer actually opens —
  sign-in and report submission — are ~67 KB gzipped and do not pull in Leaflet
  or Recharts.

## Multilingual alerting

Eight languages: English, Hindi, Assamese, Bengali, Manipuri (Meiteilon), Khasi,
Mizo and Nepali. Each state's bulletins render into a configured set, and each
recipient receives their own preferred language.

SMS part counts are surfaced because they matter: any non-Latin character forces
the message into UCS-2, cutting the payload from 160 to 70 characters per part.

> **The non-English translations are unreviewed working drafts.** A mistranslated
> evacuation instruction is worse than no instruction. Every language needs
> native-speaker sign-off from the relevant State Disaster Management Authority
> before public deployment; `app/services/i18n.py` tracks this and the API
> reports it.

## Architecture

```
backend/
  app/
    api/v1/routes/     9 route modules, 60 endpoints
    core/              settings, database, JWT auth
    data/              NER zone + road reference datasets
    ml/                physics.py, features.py, dataset.py, train.py, predictor.py
    models/            SQLAlchemy schema (11 tables)
    schemas/           Pydantic request/response contract
    services/          weather, sensors, alerts, notifications, risk_engine, i18n, seed, drill
    workers/           APScheduler jobs
  tests/               66 tests
frontend/
  src/
    components/        shared UI primitives
    lib/               api client, IndexedDB offline store, formatting
    pages/             8 route-level pages
```

**Stack:** FastAPI + SQLAlchemy 2.0 + scikit-learn on the backend; React 18 +
Vite + Leaflet + Recharts as an installable PWA on the frontend. SQLite by
default, PostgreSQL/PostGIS by changing `DATABASE_URL`.

**Scheduled jobs.** Weather polling and the risk cycle run on independent
intervals (`WEATHER_POLL_MINUTES`, `RISK_CYCLE_MINUTES`), because one is set by
what the upstream API tolerates and the other by how fast a slope can change.
Both use `max_instances=1, coalesce=True`: if a cycle runs long the next firing
is dropped, never queued behind it — a backlog would issue alerts for conditions
that have already passed.

## Configuration

Copy `backend/.env.example` to `backend/.env`. Every integration falls back to a
simulator when its key is absent, so the platform runs end to end untouched.

| Variable | Effect when unset |
| --- | --- |
| `IMD_API_KEY` / `OPENWEATHER_API_KEY` | Monsoon simulator generates rainfall |
| `BHUVAN_API_KEY` / `SENTINELHUB_*` | Cached NDVI and terrain values are used |
| `SMS_PROVIDER` (`console`/`twilio`/`msg91`) | `console` logs messages, sends nothing |
| `DATABASE_URL` | SQLite file at `backend/prahari.db` |
| `SIMULATE_SENSORS` | `true` — generates telemetry; set false for real gateways |
| `ALERT_THRESHOLD_HIGH` / `_CRITICAL` | 0.65 / 0.82 |

## Testing

```bash
cd backend && .venv/Scripts/python -m pytest tests/ -q
```

66 tests. The physics tests assert *behaviour* rather than magic numbers — a
wetter slope can never become more stable — so they stay meaningful across
recalibration. Two are regression tests for bugs found during development: the
naive/aware datetime comparison that took down the dashboard, and the batch-level
validation that would have blocked a field officer's entire offline queue.

## Before operational use

Nothing here should warn a real person until all of this is done:

1. **Retrain on a mapped inventory.** GSI or state DM authority records, via
   `python -m app.ml.train --data inventory.csv`. The bundled training set is
   synthetic and its metrics mean nothing about real-world skill.
2. **Replace terrain attributes with DEM-derived rasters.** Slope, aspect and
   curvature from a real DEM; lithology from GSI. The bundled values are
   representative defaults, not survey measurements.
3. **Calibrate the intensity–duration threshold** against local failure records.
   The coefficients in `physics.py` are literature values, not NER-fitted.
4. **Get every translation signed off** by a native speaker at the relevant SDMA.
5. **Register DLT templates** with the SMS gateway and reconcile delivery
   receipts — Indian operators silently drop unregistered transactional SMS,
   which looks like success from the API side.
6. **Independent geotechnical review** of the alert thresholds.
7. **Move to PostgreSQL/PostGIS**, put media on object storage, rotate
   `SECRET_KEY`, and remove the seeder and the demo-account list on the login
   page.
8. **Define the human decision loop.** This platform should inform an officer's
   judgement, never replace it. No evacuation should be automated.
